# SUBMISSION

## Concept

**Enterprise:** Главная водоотливная установка на горизонте 420 м рудника "Кварцитовые Горки", месторождение "Кварцитовые Горки".

**Users:** Оператор насосной установки.

**Decision:** Определить, справится ли система водоотлива с поступающей водой при отказе одного насоса.

**Why this choice:** Мы выбрали эту проблему, потому что она кажется нам интересной и серьёзной. На горизонте 420м всего два насоса, а по правилам должны быть рабочий, резервный, ремонтный. Если один в ремонте и второй откажет, то вода начнет затапливать горизонт. Это означает остановку добычи и является риском для людей. Поэтому оператору нужно заранее знать справится ли один насос при поломке второго и сколько у него есть времени. Мы выбрали реальный объект с открытыми данными чтобы цифры можно было проверить

**Real or fictional:** Объект реальный. Источник данных — [проект горных работ месторождения «Кварцитовые Горки»](https://hearings.ndbecology.gov.kz/Public/PubHearings/LoadFile/239849), страницы 130–134. В документе указаны два насоса ЦНС 300×480 на горизонте 420 м и подача каждого насоса — 300 м³/ч.

## Mine

Подземный рудник «Кварцитовые Горки» (ТОО «Казахалтын»): **главный водоотлив горизонта 420 м**. Вода с горизонтов поступает в главный водосборник, насосы ЦНС 300×480 откачивают её по нагнетательному ставу в стволе шх. «Фланговая» на поверхность.

Двойники OpenEgiz (Eclipse Ditto, пространство имён `org.kvgorki`), иерархия задана атрибутом `_parents`:

```text
mine ─┬─ shaft-flangovaya ── riser-01            (став Ø159/219 мм)
      └─ horizon-420 ─┬─ sump-01                 (главный водосборник)
                      ├─ pump-01  ── сосёт из sump-01, качает в riser-01
                      └─ pump-02  ── сосёт из sump-01, качает в riser-01
```

| Двойник | Что хранит |
|---|---|
| `mine`, `horizon-420`, `shaft-flangovaya` | структура рудника, источник данных |
| `sump-01` | объём, уровень, заполнение, приток, откачка, доступная и требуемая по ПБ производительность, время до аварийного уровня, состояние (норма / предупреждение / авария); `control.inflow_m3h` — приток, заданный оператором |
| `pump-01`, `pump-02` | паспорт ЦНС 300×480 (стр. 131); состояние (работает / резерв / выведен), подача, мощность, энергия, наработка; `control.enabled` — насос в работе или выведен |
| `riser-01` | расход на поверхность |

Связи насосов с водосборником и ставом — атрибуты `suction_from` и `discharge_to`.

Где в коде (`team/drainage/`):
- `twins.json` — описание всех двойников, `setup_twins.py` создаёт их в Ditto;
- `water_balance.py` — водный баланс водосборника; `simulator.py` — вместимость, уровни, автоматика насосов, норма ПБ, мощность; публикует состояние двойников в MQTT (`telemetry/<двойник>`, команда Ditto `merge`) и читает `control` из Ditto;
- `panel/` — плагин Grafana со схемой водоотлива и управлением, `dashboard.json` — дашборд;
- `compose.yml` — подключение к платформе (`make drainage`).

Данные идут только через платформу: `simulator.py → MQTT → Ditto → (Telegraf → InfluxDB) → Grafana`. Кнопки экрана записывают `control` в Ditto через прокси приложения OpenEgiz в Grafana, расчёт читает их из Ditto.

| Сценарий «Обесточивание» | Оба насоса выводятся из работы | Кнопка «Обесточивание»: оба насоса красные, став пустой, «До аварийного уровня ≈ 3 ч», вода поднимается до аварийного уровня | Кнопка «Вернуть норму» |
| Сценарий: свой приток / вывод любого насоса | Оператор задаёт приток (0–2000 м³/ч) и выводит или вводит любой насос | Поле «Приток воды, м³/ч» → «Применить»; кнопки «Вывести (отказ)» / «Ввести в работу» | «Вернуть норму» |

Главный результат двойника для оператора: при данных проекта **один насос ЦНС 300×480 (300 м³/ч) перекрывает максимальный приток 108 м³/ч почти втрое** и норму ПБ 129,6 м³/ч — отказ одного насоса не опасен. Опасны потеря обоих насосов (обесточивание: около 3 ч до аварийного уровня при фактическом притоке) и прорыв воды больше 300 м³/ч при одном насосе.

## What works and what does not

Проверено на Стенде (`make drainage` с нуля на Ubuntu + Docker):
- все 7 двойников создаются в Ditto, состояние обновляется каждые 2 с;
- схема, карточки и графики показывают данные двойников;
- кнопки насосов, поле притока и все сценарии меняют расчёт; панель показывает результат только после того, как его подтвердили двойники;
- после `make down` / `make up` водоотлив поднимается вместе с платформой;
- тесты расчёта: `python3 -m unittest discover -s team/drainage/tests -v` (14 тестов).

Не сделано / известные ограничения:
- после перезапуска расчёта двойники возвращаются в начальное состояние (оба насоса в работе, приток 70 м³/ч);
- моделируется только главный водосборник гор. 420 м; ступени водоотлива с нижних горизонтов (гор. 480, 540–580 м, насосы BS) учтены как общий приток;
- приток постоянный, пока его не изменит оператор (без суточных колебаний).

## Data and Assumptions

Синтетические данные: всё состояние двойников рассчитывает `simulator.py`; внешние наборы данных не используются.

Реальные параметры — из открытого документа «План горных работ разработки запасов месторождения «Кварцитовые Горки» подземным способом (корректировка ранее выполненных проектов)», ТОО «Казахалтын», опубликованного на портале общественных слушаний: [ссылка](https://hearings.ndbecology.gov.kz/Public/PubHearings/LoadFile/239849). В репозиторий документ не включён, приводятся только параметры:

| Параметр | Значение | Источник |
|---|---|---|
| Насосы главного водосборника гор. 420 м | 2 × ЦНС 300×480 | стр. 131 |
| Подача / напор насоса | 300 м³/ч / 480 м | стр. 131 |
| Двигатель | А4-400У-4МУЗ, 630 кВт, 6000 В, 1500 об/мин; масса насоса 2106 кг | стр. 131 |
| Выдача на поверхность | по стволу шх. «Фланговая», два става Ø159 и Ø219 мм | стр. 131 |
| Фактический приток, гор. 360–420 м | 65–70 м³/ч (в модели — 70) | стр. 133 |
| Максимальный приток по руднику | 108 м³/ч | стр. 133 |
| Норма ПБ | откачка суточного притока не более чем за 20 ч: 108·24/20 = 129,6 м³/ч | стр. 133 |
| Управление насосами | автоматически по уровню воды в водосборнике, очерёдность включения | стр. 134 |

Допущения (в проекте не указаны; все — константы в начале `team/drainage/simulator.py`):

| Параметр | Значение | Обоснование |
|---|---|---|
| Вместимость водосборника | 432 м³ | 4 ч максимального притока 108 м³/ч |
| Площадь водосборника | 144 м² | уровень 3,0 м при полном водосборнике |
| Уровни пуска / останова / второго насоса / аварии | 50 / 20 / 60 / 80 % | типовая схема автоматики по уровню |
| КПД насоса / двигателя | 0,70 / 0,94 | типовые значения для секционного насоса и двигателя 6 кВ; итог 596 кВт < 630 кВт по паспорту |
| Ускорение модельного времени | ×60 (1 мин = 1 ч модели) | чтобы циклы откачки были видны на Стенде |

Персональные и конфиденциальные данные не используются.

## Mine visualization

Grafana: `http://localhost:3000` (логин `admin`, пароль печатает `make up`; он же — `GRAFANA_ADMIN_PASSWORD` в `deploy/compose/.env`) → **Dashboards → OpenEgiz Examples → «Водоотлив «Кварцитовые Горки» — горизонт 420 м»**.

- Схема водоотлива в разрезе: поверхность, ствол шх. «Фланговая» со ставом, главный водосборник с уровнем воды и отметками пуска, останова, предупреждения и аварии, насосная камера с насосами Н-1 и Н-2 (вращаются при работе), поток воды по трубам.
- Карточки: время до аварийного уровня, норма ПБ, баланс воды, уровень, мощность.
- Управление насосами, притоком и сценариями «что если».
- Графики: объём воды, приток и откачка, мощность насосов.

Двойники видны также в приложении **OpenEgiz → Twins**.

## Limitations

- Вместимость и геометрия водосборника, уровни автоматики и КПД — допущения (см. выше).
- Модель не учитывает напорную характеристику насоса (подача постоянна, 300 м³/ч), время пуска насоса и износ.
- Нет реальной телеметрии рудника: состояние рассчитывается моделью.
